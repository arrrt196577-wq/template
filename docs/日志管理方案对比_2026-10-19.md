# 日志管理方案对比

- 创建及资料核对日期：2026-10-19（Asia/Hong_Kong）
- 最近修订：2026-10-21，Go 骨架接入 log/slog、请求标识、JSON 请求与异常恢复日志及敏感信息输出边界；既有集中平台资料核对日期仍为 2026-10-19。
- 状态：Java 骨架已有默认 SLF4J 与 Logback；Go 已接入 JSON 应用日志并验证请求关联与脱敏边界。跨语言字段规范、集中采集和业务审计仍未完成，集中平台尚未确定或部署。
- 适用技术栈：Java + Spring Boot + Spring Cloud、Go + Gin 两套后端；共用 Vue 3、TypeScript、Element Plus 前端。
- 相关文档：[技术栈规划](技术栈规划_2026-10-19.md)、[业务规划](业务规划_2026-10-21.md)。

## 一、对当前项目的建议

1. Java 后端基础日志已采用 Boot 默认引入的 SLF4J 与 Logback，当前仅默认控制台输出；Go 已使用标准库 log/slog 输出 JSON 到标准输出，接入 Gin 请求与异常恢复日志、服务端请求标识、服务/环境标识和 UTC 毫秒时间。访问日志不记录原始路径、查询参数、请求体或请求头，异常恢复不记录 panic 值，数据库错误仅输出类别；已通过针对性测试。后续继续落实跨语言字段和采集约定。
2. 需要集中排障时，优先评估 Alloy + Loki + Grafana；作为独立基础设施接入，避免每个派生项目重复部署一整套平台。
3. 管理操作审计保存到项目 PostgreSQL 数据库的独立审计表，由后端提供受权限保护的查询接口，Vue 管理端展示；Go 已确定关键成功事件与业务写入共用事务，失败事件独立记录。集中日志平台可接收副本，但不作为唯一业务审计记录。

Java 基础日志依赖与 Go 应用日志已落地；Go 操作审计已确定方向但尚未实现，集中平台仍为候选建议。若团队已有 Elastic 或 Graylog 平台和维护经验，应优先评估复用现有设施。

## 二、先区分日志输出与日志管理

| 层面 | 解决的问题 | 对当前模板的建议 |
| --- | --- | --- |
| 应用日志输出 | 程序如何记录异常、请求信息和运行状态 | 使用统一日志 API、格式和字段，输出到标准输出或滚动文件 |
| 集中日志管理 | 如何跨服务采集、存储、检索、展示和告警 | 从下列平台中按部署与查询需求选择，独立于业务工程维护 |
| 管理操作审计 | 谁在什么时候对哪个对象执行了什么操作，结果如何 | 在业务侧可靠保存必要字段，提供受权限控制的只读查询 |

SLF4J、Logback 与 Loki、Elastic、Graylog 位于不同层，能够组合使用。Spring Boot 使用常见 starter 时默认采用 Logback，并支持控制台、文件与结构化日志配置，见 [Spring Boot 日志文档](https://docs.spring.io/spring-boot/reference/features/logging.html)。具体结构化配置能力以最终选择的 Spring Boot 版本为准。

本段关于 SLF4J、Logback 与 Spring Boot 的说明仅适用于 Java 后端。Go 已选用支持结构化日志的标准库 [log/slog](https://pkg.go.dev/log/slog)；后续接入集中平台时，按相同字段和采集约定提供日志，并分别验证请求关联与脱敏效果。

## 三、集中管理平台候选对比

下表中的维护成本是针对小规模自建场景的架构判断，不是性能测试结论；实际资源消耗取决于日志量、保留期、查询模式和可用性要求。

| 方案 | 典型组合 | 优势 | 主要代价 | 适用场景 |
| --- | --- | --- | --- | --- |
| Loki + Grafana | Alloy 采集，Loki 存储与查询，Grafana 展示 | 按环境、服务和时间定位日志的方式清晰，可与 Grafana 生态配合 | 需设计标签、学习 LogQL，管理持久化、保留和访问控制；大范围正文检索需要评估扫描成本 | 多个服务或实例的日常排障，通常能够先确定服务和时间范围 |
| Elastic Stack | Elastic Agent 或 Filebeat 采集，Elasticsearch 索引，Kibana 展示；Logstash 按需加入 | 全文检索、结构化字段筛选、聚合分析和可视化能力丰富 | 需管理字段映射、索引、分片、存储及生命周期，集群维护要求较高 | 经常跨服务、跨较长时间范围进行复杂检索和多维统计，或已有 Elastic 基础设施 |
| Graylog | Graylog、Data Node 和 MongoDB，加对应日志采集入口 | 产品围绕日志采集、处理、搜索和管理工作台组织，便于配置集中管理流程 | 仍需维护搜索存储与 MongoDB，功能需核对具体版本和产品方案 | 希望使用现成日志管理工作台，存在多种日志来源，或已有 Graylog 运维经验 |

### Loki：优先按服务与时间排障

Loki 对日志流标签建立索引，不对正文建立传统全文倒排索引；正文仍可通过查询过滤。它适合先缩小服务与时间范围，再查关键字或请求标识。不能据此保证它在所有场景都比 Elastic 更省资源或更快，见 [Loki 架构](https://grafana.com/docs/loki/latest/get-started/architecture/)。

建议仅把服务、环境等低基数字段作为索引标签。`traceId`、`requestId`、用户 ID 等大量变化的值保留在日志正文或结构化元数据中，避免日志流数量膨胀，见 [Loki 标签说明](https://grafana.com/docs/loki/latest/get-started/labels/)。

新项目应评估 [Grafana Alloy 采集方式](https://grafana.com/docs/loki/latest/send-data/alloy/)。[Promtail 官方说明](https://grafana.com/docs/loki/latest/send-data/promtail/)已标明其于 2026 年 3 月 2 日结束生命周期，不应作为新模板的默认采集器。

部署不能只考虑运行一个容器：Loki 本身不包含认证层，应保护其写入和查询 API，见 [Loki 认证要求](https://grafana.com/docs/loki/latest/operations/authentication/)。同时需要确定存储持久化、保留周期及容量监控，见 [Loki 存储说明](https://grafana.com/docs/loki/latest/configure/storage/)。

### Elastic：优先复杂检索与分析

如果经常需要按异常片段、业务标识、接口及状态码等条件组合查询，并做多维聚合分析，Elastic 值得优先评估。可从 Agent 或 Filebeat 直接采集开始；复杂转换、富化或多目标路由时再加入 Logstash，并非必须部署完整 ELK 组合，见 [Elastic 日志管理文档](https://www.elastic.co/docs/solutions/observability/logs)。

需要关注字段类型、索引与分片规模、生命周期和磁盘规划，不能只计算日志原文大小，见 [Elastic 分片与资源规划](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards)。高级能力是否可用应在实际选型时核对产品方案。

若团队已有 OpenSearch，也可作为同类索引检索方案评估。其官方日志摄取示例使用 Fluent Bit、Data Prepper、OpenSearch 和 Dashboards，见 [OpenSearch 日志摄取说明](https://docs.opensearch.org/latest/observing-your-data/log-ingestion/)。它同样需要索引与存储运维，不直接视为轻量替代。

### Graylog：优先现成日志管理工作台

Graylog 当前推荐的基础组合包括负责处理与展示的 Graylog、负责日志存储与索引的 Data Node，以及保存元数据和配置的 MongoDB，见 [Graylog 架构说明](https://go2docs.graylog.org/current/planning_your_deployment/the_graylog_stack.htm)。

它适合需要统一接入、组织和查询不同来源日志的团队。但不能将它理解为只需维护一个 Web 服务；告警、归档、权限等具体能力应逐项核对所选产品方案，见 [Graylog 功能对比](https://graylog.org/graylog-features/)。

## 四、第一期如何落地

### 必做：统一输出与业务审计

- 开发环境保留易读日志；部署环境使用约定的结构化 JSON，按容器或虚拟机部署方式选择标准输出或滚动文件。
- 建议约定时间、级别、服务、环境、实例、日志消息、异常及请求关联字段；时间格式和时区必须一致。
- 建立 `requestId` 关联请求；接入链路追踪后补充 `traceId`、`spanId`，并验证跨服务及异步调用的上下文传播。
- 各派生项目为所选后端配置服务标识；Java、Go 模板保持字段含义、时间格式及审计事件语义一致，便于复用前端审计页面，不要求汇集不同项目的日志或共享审计数据。
- 关闭不必要的敏感请求体记录，对密码、登录凭据和其他敏感字段脱敏；控制日志级别、轮转与保留策略。
- 操作审计与业务提交结果保持一致，定义审计写入失败时的处理策略；登录失败等无业务提交的事件独立记录。
- Vue 管理端实现审计查询；技术排障优先使用集中平台现有界面，避免在模板内重复开发完整日志工作台。

Spring Boot 可通过 Micrometer Tracing 将追踪标识关联到日志，但该能力依赖实际接入和上下文传播配置，不能仅凭采用 Spring Cloud 就假定已经具备，见 [Spring Boot 链路追踪文档](https://docs.spring.io/spring-boot/reference/actuator/tracing.html)。

上述追踪实现说明仅适用于 Java 后端；Go 后端的追踪组件与 Gin 上下文传播实现仍待选型，不能据此视为已接入。

### 按需：集中日志接入

建议的 Loki 接入路径为：应用结构化日志 → Alloy → Loki → Grafana。提供独立的采集与部署示例，集中平台不是前后端工程基础启动的强制条件。

应用避免同步依赖远端日志平台；采集过程需要评估缓冲、重试、磁盘耗尽与丢弃策略。基础输出不等于可靠归档，单机文件也不等于集中管理。

若当前只有少量实例且无需跨机器查询，先完成基础输出和审计即可；当排障开始需要人工逐机查找时，再启用集中采集。存在复杂分析需求时直接评估 Elastic，已有平台时优先接入现有平台。

## 五、最终选型仍需确认

1. 部署方式与规模：虚拟机、Docker 或 Kubernetes，服务和实例如何分布，是否已有日志平台。
2. 数据量与生命周期：预计每日写入量、保留天数，以及持久化、备份和可用性要求。
3. 查询习惯与维护能力：主要按服务和时间排障，还是经常做全局全文检索、多维分析；团队能维护哪些组件。
4. Go 已接入 slog、Gin 请求与异常日志、请求关联和脱敏边界；业务审计与失败处理、两套后端的统一字段和审计一致性验证仍待落实。

这些信息目前不确定，因此本文不提供固定硬件配置、吞吐承诺或精确费用，也不将任何集中日志平台记录为已选定。
