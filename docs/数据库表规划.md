## 四、物理结构与约束规划

### 员工表 `employee` 专项

字段含义、类型与业务规则见[员工管理](业务/员工管理.md#二员工表-employee)，本节仅维护物理约束及索引要求；以下尚无迁移实现：

- 主键为 `id`，按共享表基线建立非空 `tenant_id` 到 `tenant.id` 的外键，并增加 `UNIQUE (tenant_id, id)`，供后续同租户关联引用。
- 工号采用 `UNIQUE (tenant_id, employee_no)`，离职不释放。规范化字符规则明确后同步应用校验与数据库约束；姓名、工号应拒绝空白。
- 账号绑定采用普通 `UNIQUE (tenant_id, admin_user_id)`，保持 PostgreSQL 默认 NULL 互不相等的语义，允许多个未绑定员工；不使用将 NULL 视为相等的唯一性设置。
- `(tenant_id, department_id)`、`(tenant_id, admin_user_id)` 分别复合引用 `department (tenant_id, id)`、`admin_user (tenant_id, id)`；被引用表须先具备相应唯一约束。可空关联使用默认 MATCH SIMPLE，不因租户非空而要求关联 ID 必填。
- CHECK 限定 `employment_status IN ('employed', 'departed')`，并限定 `(employment_status = 'employed' AND left_on IS NULL) OR (employment_status = 'departed' AND left_on IS NOT NULL AND left_on >= hired_on)`；状态、入职日期均非空。
- 部门与绑定账号外键采用 `ON DELETE RESTRICT`，避免删除导致员工档案或绑定关系被隐式改写；不级联删除员工。操作者外键待身份边界完整确定后再加，不混用平台、会员 ID。
- 列表基线索引为 `(tenant_id, created_at DESC, id DESC)`；部门筛选索引按实际查询评估。不为工号、账号绑定重复建立普通索引，不为手机邮箱增加唯一约束。
- 建表先满足租户、部门与账号目标约束，再创建员工与岗位关联；组织表完整设计和迁移顺序需在员工模块实施前补齐。

### 通用要求

以下为建表时需落实或确认的设计清单，不视为已经执行的 DDL。

| 项目 | 规划要求或建议 | 待落实内容 |
| --- | --- | --- |
| 主键 | 已有 Go 实体使用 `int64`；业务规划建议 PostgreSQL `bigint` identity | 确认生成方式及 Java 映射；接口 ID 表达另按共同契约确定 |
| 命名 | 建议表、列、约束和索引采用有业务含义的 `snake_case` | 新表定稿时记录实际名称，避免含糊缩写 |
| 租户归属 | 若采用共享表，租户表使用非空 `tenant_id`，无默认租户；平台表不强加该字段 | 确认隔离方案，补充实体与租户外键 |
| 账号唯一性 | 建议两个账号表分别使用 `(tenant_id, username)` 唯一约束 | 确认用户名规范化规则；数据库约束兜底并发重名 |
| 同租户关联 | 建议被引用表增加 `(tenant_id, id)` 唯一约束，关系表使用复合外键 | 逐项明确用户、角色及后续会员关联的同租户约束 |
| 关系去重 | 用户角色、角色权限关系应有覆盖租户和关系两端的唯一约束 | 确认字段；重复授权不能产生重复关系记录 |
| 凭据版本 | `auth_version` 非空默认 1，增加正整数约束；改密或重置时与哈希同事务递增 | 补充迁移、事务与认证版本比较；当前均未实现 |
| 状态与文本 | 对已确认的枚举、必填文本、长度和格式建立必要约束 | 不猜测未提供的终端枚举；不以实体标签代替校验 |
| 时间与空值 | 当前时间点映射 `timestamptz(3)`，生日映射 `date`；可选字段按业务规则使用 NULL | 更新时显式维护 `updated_at`；确认 Java 时间映射 |
| 操作者引用 | 明确平台、租户管理端、会员及系统操作身份 | 在身份范围明确前，不添加可能串租户或混用身份的操作者外键 |
| 删除规则 | 账号、角色、租户的停用不级联删除业务数据；示例删除方式另行确定 | 每条外键明确删除行为；审计保留策略单独确定 |

### 索引规划

- 登录查询优先利用已确认的租户内用户名唯一索引，不为相同列重复建立普通索引。
- 租户内按创建时间分页的列表，建议评估 `(tenant_id, created_at DESC, id DESC)`；排序与筛选最终按共同契约及实际查询确定。
- 关系表除去重约束外，按用户查角色、按角色查用户等实际访问方向评估索引。
- 审计先明确租户、时间、操作者和事件类型的查询组合，再确定复合索引与保留策略。
- 不为每个字段预建索引；状态、昵称模糊检索和 JSONB 检索索引按数据量、查询及执行计划决定。

## 五、迁移与初始化顺序

1. 确认多租户隔离、账号归属、平台身份及首批交付范围，补齐必要的共同契约。
2. 定稿首批表的字段、主键、唯一性、外键、CHECK 和索引；同步业务规划与两套后端的实体映射。
3. 若采用共享表，先建立租户目录，再建立账号、角色和关联表；依赖目标未建立前不提前增加外键。示例及审计按功能依赖安排。
4. Java 使用 `backend-template/java/template-app/src/main/resources/db/migration/` 下的 Flyway 版本化 SQL；Go 使用 `backend-template/go/migrations/sql/` 下的 goose 版本化 SQL。按各自已有约定维护，不在同一数据库同时运行两套迁移器。
5. 通过受控初始化流程创建租户、管理员和必要角色关系；具体流程与幂等规则待定，不在迁移中写入固定生产密码或真实密钥。
6. 分别在 Java、Go 独立环境验证空库迁移、已有版本升级与初始化幂等；已执行的迁移不直接修改，后续变更新增版本。

当前没有业务表，可在首个迁移前统一设计。已有数据的派生项目需另行制定回填、查重与约束收紧步骤，不能直接填入默认租户。Go 不使用 `AutoMigrate` 建业务表；迁移回退或前向修复方案在发布前明确，不默认删除数据回退。

## 六、建表验证清单

- [ ] 空库迁移后，实际列类型、默认值、空值和约束与定稿设计一致。
- [ ] 重复执行迁移不重复建表，初始化不重复创建租户和管理员。
- [ ] 并发创建同租户重名账号时只有一个成功；不同租户同名行为符合确认后的规则。
- [ ] 缺失或无效租户、跨租户用户角色关联被数据库约束及服务端拒绝。
- [ ] 空哈希、非法状态、非正凭据版本及其他已确认的非法值被拒绝。
- [ ] 改密失败时哈希与版本一并回滚；成功后旧凭据按业务规则失效。
- [ ] 会员可空字段、生日、IP、JSONB 标签等映射往返正确。
- [ ] 最后管理员保护、授权变更和租户禁用的并发场景经过服务层验证，不能仅凭外键或 CHECK 宣称已保障。
- [ ] Java、Go 分别记录迁移与业务集成结果，文档状态随实际实现更新。

## 七、建表前需要确认的关键事项

1. **隔离与身份**：是否采用共享库共享表；账号是否只属于一个租户；是否采用独立平台身份。这些决定租户列、唯一键及外键。
2. **首批表与规则**：角色和权限关系、管理员判定、审计身份、会员功能范围及示例删除方式。未确认前不补造完整字段或直接执行建表。
3. **数据库与迁移交付**：PostgreSQL 生产基线、两套后端表结构和 SQL 的复用边界、初始化及升级恢复流程。
