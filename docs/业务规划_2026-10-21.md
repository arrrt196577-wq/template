- 相关文档：[技术栈规划](技术栈规划_2026-10-19.md)、[API 规划](API规划_2026-10-20.md)（接口与鉴权建议，尚待确定）。

### 一、第一期目标

交付 Java 与 Go 两套可独立使用的后端模板，以及一套共用的管理端前端。每套后端均能从空数据库启动、完成登录与授权、支持标准管理页面并追溯关键操作。后续项目可按语言选择后端，基于完整链路复制和扩展自己的业务模块。

第一期优先解决可运行、可复用和权限边界三个问题，控制产品功能与基础设施范围。

### 二、规划前提与边界

- Java、Go 后端遵循同一份接口契约和本规划中的服务端功能要求，分别实现、联调和验收；F05 为共用前端能力，须分别对接两套后端验证。
- 每个派生项目仅选择 Java 或 Go 其中一套后端，并复用前端模板；不设计同一项目内的双后端部署或运行时切换。两种组合在模板各自独立的验收环境中验证，各派生项目独立管理数据库及登录状态。
- 两套后端通过 Authorization: Bearer 传递 Token，暂不采用 Cookie 承载认证凭据；Go 已确定随机不透明 Token + PostgreSQL 会话记录、Argon2id 与 RBAC 中间件。Java Token 类型与组件、前端存储、有效期、刷新、多端登录及并发细则仍待细化，尚无登录实现。
- 后续多租户需求已明确，提前规划租户归属、身份与隔离，见[多租户业务与隔离](#多租户业务与隔离)；当前没有租户字段和隔离实现，实际交付范围与阶段待方案确认。组织、部门及复杂数据范围仍暂缓；个人资料和密码严格限制为本人操作。
- 示例数据共享规则收敛到租户范围：未来启用多租户时，仅具备对应权限且属于同租户的账号可访问示例记录；私有数据另行定义访问范围。
- 权限采用用户关联角色、角色关联权限的 RBAC 模型；权限标识由代码维护，前端菜单与按钮映射这些标识。
- 第一期开设角色授权页面，菜单结构及权限目录由代码维护，暂不开发动态菜单和权限定义编辑器。
- Spring Cloud 已纳入 Java 后端技术栈，具体组件、服务边界和部署拓扑仍待细化；网关、注册中心及配置中心不默认全部纳入首期交付，Go 后端配套基础设施另行按需评估。
- 主数据库统一选定 PostgreSQL，生产版本基线待定；Java 已接入 MyBatis-Plus + Flyway 依赖与配置，Go 已接入 GORM + goose、slog 与 testing + httptest，固定版本见技术栈规划。两套后端均无业务表、业务迁移 SQL 或持久化业务；Go 已用 PostgreSQL 18.6 验证连接、迁移与事务基础能力。

### 三、第一期必做功能

#### F01 工程与接口基线

实现内容：

- 分别建立 Java、Go 后端工程及共用前端工程，各自提供配置示例及开发环境说明，区分开发、测试与生产所需配置。
- 建立数据库迁移和受控的初始管理员创建流程，避免重复初始化和公开固定生产密码。
- 统一接口响应、参数校验、异常处理、分页与排序约定，以及前端请求和错误提示方式。
- 定义两套后端共用的接口路径、方法、认证交互、字段类型、HTTP 状态码、错误语义、时间格式和权限标识，使用同一组契约场景验证；两种语言内部的组件与实现方式分别选型。
- 明确未登录、无权限、参数错误及业务冲突的响应语义；错误响应中不暴露堆栈和敏感配置。
- 提供基本健康检查和应用日志，便于确认启动状态及定位请求失败。

验收：两套后端分别按说明从空数据库启动，重复启动不会重复创建初始化数据；共用前端分别完成真实接口请求，非法参数均能够在服务端被拒绝，相同契约场景的对外行为一致。

#### F02 登录、会话与个人中心

实现内容：

- 用户名与密码登录、退出、当前用户信息查询、登录过期处理，以及基础的登录失败限流。
- 按 Token 方向设计登录凭据签发、请求校验与失效处理；本文中的“会话”指登录状态及其生命周期，不代表选用 Cookie。
- 密码使用安全的单向哈希存储，接口不返回密码哈希；不在日志中记录密码或登录凭据。
- 个人中心支持修改昵称和本人密码；修改密码验证原密码，账号身份以服务端认证结果为准。
- 退出后当前会话失效；账号禁用后旧会话不可继续访问受保护接口；密码修改或重置后所有旧会话失效，要求重新登录。
- 角色或权限变更后，下一次受保护请求按最新有效权限判定，不能一直沿用登录时的授权结果。

验收：分别验证正确登录、错误登录、退出、过期、禁用和密码变更；原凭据在对应失效条件下不可继续使用；篡改用户 ID 无法修改他人资料或密码。

#### F03 用户管理

实现内容：

- 用户列表、分页、账号或昵称筛选，以及启用状态筛选。
- 创建账号、修改基本资料、启用或禁用账号、分配角色、由系统管理员重置密码。
- 账号唯一性与字段校验由服务端执行；用户管理和角色分配接口独立受权限控制。
- 防止通过禁用、撤销角色或权限等操作使系统失去最后一个可用管理员。
- 第一期以禁用作为账号退出使用的方式，暂不提供用户删除和批量操作。

验收：管理员能够创建并授权一个新账号，新账号能够登录；重复账号被拒绝；无管理权限者无法直接调用管理接口；管理员保护规则无法被绕过。

#### F04 角色与权限管理

实现内容：

- 角色列表、创建、修改、停用及权限分配，支持一个用户关联多个角色。
- 通过固定权限目录勾选授权，至少覆盖用户、角色、示例记录与审计查询所需权限。
- 权限按具体操作区分，至少能分别控制示例记录的查询、新建、修改与删除；角色管理及授权操作由系统管理员执行。
- 服务端默认拒绝未经授权的受保护操作；前端根据服务端返回的有效权限控制路由、菜单和按钮。
- 停用角色后，该角色不再贡献权限；角色被用户关联时不直接删除，第一期不提供角色删除入口。

验收：创建只读角色并分配给普通账号；该账号可以查询示例记录，但直接调用写接口返回无权限结果；为同一会话撤销查询权限后，下一次查询被拒绝。

#### F05 管理端基础框架

实现内容：

- 登录页、基础布局、侧边导航、顶部用户入口及面包屑导航。
- 登录态路由处理、权限受限提示、403 与 404 页面。
- 登录后进入用户有权访问的页面；没有业务菜单时提供清晰提示，并保留个人中心和退出入口。
- 统一处理加载、空数据、表单校验、操作确认、请求失败和登录过期。
- 菜单及按钮可见性与后端权限保持一致，支持刷新页面和直接访问链接。

验收：登录后刷新和直接访问合法链接正常；无权限页面、失效登录和不存在的地址各有明确反馈；只读账号界面与实际可调用权限一致。

#### F06 标准 CRUD 示例

实现内容：

- 提供一个可替换的中性“示例记录”模块，包含编码、名称、状态、备注和必要的时间字段。
- 打通列表、分页、筛选、详情、新建、修改与单条删除，数据实际持久化。
- 前后端均有字段校验，服务端约束编码唯一性、分页大小和允许排序的字段。
- 删除操作有确认提示，操作成功后列表正确更新；各种操作分别执行权限校验。
- 说明如何沿用示例新增一个业务模块，以及应替换的字段、接口、权限和数据访问规则。

验收：新增记录后刷新仍然存在，修改和删除结果与数据库一致；非法输入、重复编码和未经授权的读写均被服务端拒绝。

#### F07 基础审计

实现内容：

- 记录登录成功与失败，以及账号状态、密码重置、角色授权和示例记录写操作等关键事件。
- 记录事件时间、操作者、操作类型、对象标识和操作结果，提供便于关联请求的标识。
- 仅记录必要且经过筛选的字段，不保存原始密码、密码哈希、会话标识或令牌；失败操作不能记录为成功。
- 提供受权限控制的日志分页查询，支持按时间、操作者及操作类型筛选。
- 第一期开设只读查询入口，不提供日志修改、删除和导出功能；应用日志与审计记录分别承担故障定位和管理操作追溯职责。

验收：关键操作可查询并定位到操作者及对象；普通账号无法查询审计记录；抽查日志不包含敏感凭据。

### 一、建模边界

用户提供的 `AdminUserDO` 可以对应一张管理用户表，建议命名为 `admin_user`。表保存账号、密码哈希、资料、状态与最近一次成功登录信息；会话、角色及用户角色关系使用独立表，后续逐张规划。

不直接照搬 Java 继承结构和 ORM 注解：

1. `TenantBaseDO` 源码尚未提供，其继承字段不确定。现有实体按此前单租户边界实现，未含 `tenant_id`；根据新增需求后续按本文多租户章节调整。本文显式列出审计字段，不假定就是原基类完整内容。

3. `password` 改名为 `password_hash`，沿用 Go 已选定的 Argon2id。原实体中的 BCrypt 注释不适用于本项目 Go 实现；Java 的密码实现仍按其后续选型确定。

邮箱、手机、性别和头像按本次参考实体纳入可选字段草案；这不代表首期已经增加邮箱或手机登录、资料编辑接口、头像上传等功能。

#### 2.2 账号与资料规则（建议）

- 用户名：输入先去除两端空白，再将 ASCII 大写字母转为小写；规范值限制为 3–64 个 ASCII 字符，只允许小写字母、数字、下划线、点和连字符。数据库保存规范值，并设置同样的格式约束与唯一约束，避免只靠应用预查询导致并发重名。该规则尚待确认，不默认支持中文账号或手机号登录。
- 昵称：去除两端空白后为 1–64 个 Unicode 码点；Go 和 Java 采用一致的长度口径。账号创建后首期建议不支持修改用户名，避免登录标识变更规则不完整。
- 可选文本：建议将空串或全空白规范为 `NULL`；非空时执行长度和格式检查。密码原文不得 trim，密码长度与强度规则另行确认，不能用哈希列长度代替输入规则。
- 联系信息：邮箱、手机是否验证及号码格式尚未确定；暂不据此授权、登录或找回密码。展示和日志只保留业务必要信息。
- 头像：存储地址不代表允许后端主动抓取任意 URL；上传、地址来源和前端展示限制在实际开放功能前确定。

### 三、写入、认证与审计边界

- 持久化实体、业务类型与 HTTP DTO 分离。响应 DTO 不包含 `password_hash`；更新按白名单映射，客户端不能直接修改 ID、哈希、角色、创建人或最近登录信息。备注和联系方式也应按权限选择性返回。
- 创建用户必须通过密码组件生成哈希，不设置默认密码；初始管理员通过受控命令创建，具体交互和幂等策略待定。管理员身份由后续 RBAC 模型确定，不以 `id = 1`、用户名或额外的 `is_admin` 字段推定。
- 登录成功并建立会话时才更新 `last_login_at`、`last_login_ip`；并发登录应保证较早的成功事件不会覆盖较新的时间及其对应 IP。失败登录不覆盖成功登录信息，另写失败审计。IP 来自已经配置可信代理边界的服务端解析，不能直接信任客户端传入字段。
- 最近登录字段只提供摘要，不能替代登录历史、会话记录或关键操作审计。`created_by`、`updated_by` 也不能替代完整审计事件；登录摘要自动更新时不冒充某个后台资料修改操作者。
- 禁用账号、修改或重置密码必须按既定要求撤销旧会话；账号变更、会话撤销和关键成功审计写入应在同一事务中完成。重新启用账号不得恢复被撤销的会话。
- 仅靠本表无法保证并发登录与改密/禁用时的撤销边界，也无法保护最后一个可用管理员。相关用例须结合会话、角色关系以及明确的锁或其他并发控制另行设计和测试。
- `timestamptz` 保存时间点，应用与数据库连接使用统一 UTC 约定；HTTP 时间表达仍须在共同契约中确认，不能直接照搬无时区的 `LocalDateTime` 表达。

### 一、隔离方式与数据归属

建议采用 PostgreSQL 共享库共享表，使用非空 `tenant_id` 隔离租户数据，沿用现有单应用与数据库工具，减少逐租户迁移和连接管理成本。如果需要租户独立备份恢复、专属部署或更强的物理隔离，需改评估独立数据库方案；这些需求目前不确定。

| 数据 | 建议范围 | 说明 |
| --- | --- | --- |
| 租户目录 `tenant` | 平台 | 租户信息、可用状态 |
| 平台账号 `platform_user`（候选） | 平台 | 独立身份，不混入租户账号表 |
| `admin_user` | 租户 | 管理端账号，超级管理员角色也仅在本租户生效 |
| `member_user` | 租户 | 普通会员，与管理端是不同身份 |
| 角色、用户角色、角色权限、示例记录 | 租户 | 授权和业务资源都必须隔离 |
| 会员等级、标签、分组、积分流水（后续） | 租户 | 关联目标必须属于同一租户 |
| 权限标识目录、明确的公共地区字典 | 平台公共 | 权限目录公共不代表角色授权公共；地区字典范围待定 |
| 会话、审计 | 按身份区分 | 租户会话和事件包含租户，平台范围独立定义 |

建议一条管理账号或会员记录只属于一个租户。同一自然人跨租户使用独立账号、凭据和资料。如果要全局账号加入多个租户，应采用全局身份加租户成员关系，不能仅给当前用户表加字段。

本轮提前规划数据与身份边界；套餐、计费、域名管理、自助开通、跨租户数据搬迁不自动纳入首期功能。

### 二、表结构与完整性

#### 2.1 租户表 `tenant`（草案）

| 字段 | 建议类型 | 规则 |
| --- | --- | --- |
| `id` | `bigint` identity | 主键 |
| `code` | `varchar(64)` | 非空、全局唯一、规范化，建议创建后不变；登录选择租户的候选标识 |
| `name` | `varchar(128)` | 非空，展示名称 |
| `status` | `varchar(16)` | `enabled`、`disabled`，默认启用 |
| `created_at`、`updated_at` | `timestamptz(3)` | 非空，更新时显式维护 |

暂不增加套餐或到期时间；新增到期机制时再定义访问和会话失效行为。停用租户不级联删除账号、业务数据和审计。

#### 2.2 账号与关联表调整方向

- `admin_user`、`member_user` 新增 `tenant_id bigint NOT NULL`，引用 `tenant.id`。禁止默认租户，不用 0 或 NULL 表示平台账号；普通更新不能修改归属。
- 保留全表唯一 `id` 主键，同时增加 `UNIQUE (tenant_id, id)`，供关联表的复合外键引用。
- 用户名改为 `UNIQUE (tenant_id, username)`，两个账号表各自约束；跨租户可同名。手机邮箱是否用于登录、如何规范化与租户内唯一，另行确定。
- 角色编码、示例编码等采用租户内唯一约束。列表索引建议按查询增加 `(tenant_id, created_at DESC, id DESC)`，替换原无租户索引草案。
- 用户角色表同时用 `(tenant_id, user_id)`、`(tenant_id, role_id)` 引用同租户的用户与角色；会员等级、分组关系同理。只关联 `id` 只能证明记录存在，不能保证租户一致。PostgreSQL 支持多列唯一约束与外键，见[官方约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html)。
- 会员 `TagIDs` 当前为 JSONB，无法逐项建立复合外键；后续写入须验证每个标签归属。正式启用标签管理时建议迁移到含 `tenant_id` 的关联表，将 `TagIDs` 作为查询投影，避免两份持久化关系来源。
- `created_by`、`updated_by` 先保留，写入用例须明确其身份范围，不能混写平台、管理端与会员 ID。审计应表达操作者类型、ID、资源租户；平台跨租户操作另记录平台身份，不能冒充租户用户。

### 三、登录与会话

1. 登录前确定目标租户，建议共同契约增加 `tenantCode`，域名映射为候选替代；具体入口与字段待定。租户标识是选择目标，不是凭据。
2. 账号查询同时限定租户、用户名和身份体系，检查租户及账号状态；管理端与会员登录入口区分。失败提示避免泄露账号存在性，限流考虑来源 IP 与租户账号组合。
3. 会话绑定账号、租户和身份类型。管理端、会员会话建议独立表或采用有明确完整性约束的共同模型，具体结构待定；Token 仍不透明。
4. 受保护请求从已验证会话建立服务端租户上下文，客户端请求头、路径或正文不能覆盖它；若仍传租户标识，必须与会话一致，否则拒绝。
5. 每次请求检查租户状态、会话、账号及最新权限。缺失上下文必须拒绝租户业务访问，不能降级为全表查询或默认租户。
6. 切换租户建议重新认证并签发目标会话；不能修改请求头直接切换。若采用全局成员模型则另设计切换授权。
7. 禁用租户后后续租户请求拒绝，并撤销全部旧会话；重新启用不恢复旧会话。并发登录与禁用须协调事务或锁，具体机制待实现设计。

授权必须同时检查身份范围、同租户、接口权限和本人或其他数据范围。最后一个可用管理员保护按租户分别计算，平台管理员另行定义；租户超级管理员不能跳过租户过滤。

### 四、查询与平台管理

- Repository 要求显式租户范围或受控的租户实例。列表、总数、详情、更新、删除、关联及原生 SQL 都限定租户；INSERT 归属由服务端赋值，UPDATE 不得改变归属。
- 结构体标签、嵌入、通用 ORM 回调与前端筛选均不等于完整隔离；公共封装也须覆盖跨租户验证。
- 已有接口权限但资源属于其他租户时，建议返回 404，避免暴露其存在性；共同契约落实时确认错误语义。
- 平台入口、身份、权限与 Repository 能力独立。禁止“超级管理员自动忽略租户”或客户端可传的 `skipTenant`；跨租户操作明确指定目标、授权并审计。
- 后台任务、批处理与业务管理命令显式建立租户范围。未来缓存键、文件路径、幂等键、导出任务和消息负载都纳入租户与身份范围。
- PostgreSQL RLS 可作数据库侧补充防护候选，尚未选定或实现。若采用，验证表所有者和 BYPASSRLS 绕过行为，以及连接池租户上下文复用，不能仅设置连接级变量就假定安全。见[官方行级安全文档](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)。

### 五、Go 字段复用方向

建议在 `internal/platform/persistence/` 分别定义 `AuditFields`、`TenantFields`，由业务 `postgres` 适配包按需嵌入，业务根包继续不依赖 GORM。分开定义，避免平台账号、租户目录、公共字典被迫携带租户字段。

```go
// 设计示意，尚未加入实际代码。
type TenantFields struct {
    TenantID int64 `gorm:"column:tenant_id;type:bigint;not null;<-:create"`
}

type AdminUser struct {
    TenantFields
    AuditFields
    // 账号与资料字段……
}
```

嵌入只复用字段映射，不生成安全边界。租户字段无默认值，后续必须校验有效性并落实外键；认证上下文与查询隔离另行实现。

### 六、实施与验收顺序

1. 确认隔离方式、账号归属及平台账号模型；补齐 Java、Go 与前端共用的登录和会话租户契约。
2. 编写租户与账号迁移，调整现有实体公共字段与租户字段。当前无业务表，可在首个迁移前按确认方案设计；已有数据的派生项目需单独回填、查重、再收紧约束，不能直接套默认租户。
3. 实现上下文、租户限定 Repository、身份分流、会话与事务约束，再开放业务接口。
4. 至少使用两个租户验证：同名登录、伪造租户、Token 租户不一致、跨租户详情/列表总数/写操作、跨租户角色及会员关联、租户禁用与重启用、平台越权和各租户最后管理员保护；后台任务、缓存等在引入时补测。
5. Java、Go 分别通过相同隔离场景，不能用一套或一个默认租户通过代替完整验收。

本轮仅修改规划，不修改 Go 实体和运行接口，也不执行数据库迁移。实际多租户交付范围与阶段在方案确认后细化。

### 七、需要确认的产品边界

1. 共享库共享表是否满足要求，是否需要客户独立备份恢复或专属部署。
2. 一个账号只属于一个租户，还是全局账号可以加入多个租户。
3. 平台是否采用独立账号体系；登录用租户编码还是域名选租户。
