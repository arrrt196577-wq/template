- 导航：[文档索引](../文档索引.md)、[业务范围与阶段](../业务/业务范围与阶段.md)。

模块路径与授权边界分别见[认证与个人中心](认证与个人中心.md)、[用户管理](用户管理.md)、[角色与权限](角色与权限.md)、[示例记录](示例记录.md)、[审计](审计.md)及[多租户](多租户.md)。Token 交互与失效细则在认证模块维护，本文仅维护公共约定。

## 一、目标与已明确前提

1. Java + Spring Boot + Spring Cloud、Go + Gin 各开发一套完整后端模板；每个派生项目只选择其中一套后端，并复用 Vue 管理端模板。
2. 复用对象是接口契约、前端请求代码与数据类型、验收场景。各派生项目独立部署、管理数据库及认证凭据，不设计同一项目中的双后端部署、运行时切换或跨语言 Token 互认。
3. 两套后端使用 Authorization: Bearer 传递 Token，暂不采用 Cookie 承载认证凭据；认证方向已调整为 JWT + Redis 登录有效记录；会员支持多端独立登录，单次登出不影响其他登录。两套后端组件、前端存储、有效期、刷新、管理端多端策略与并发撤销机制仍待定。
4. 功能与安全要求沿用业务规划，包括服务端授权、本人数据边界、最后一个可用管理员保护、及时撤权和旧凭据失效。

本规划的目标是让派生项目选用任一后端模板时，都能沿用相同前端业务页面与请求逻辑。接口一致不要求数据库表、内部实体、框架组件或服务拆分方式一致。

## 二、契约维护方式（建议）

- 采用契约优先流程：先定义一份与语言无关的 OpenAPI 契约，再分别开发 Java、Go 实现和前端调用。
- OpenAPI 定义路径、方法、参数、请求响应、必填与可空约束、状态码、认证方式和示例；授权生效时机、撤销规则及事务结果等行为另以场景描述和验收用例补充。
- 维护一份人工可审查的契约作为接口定义入口。实现中生成的文档只能作为核对产物，避免两套后端分别维护一份独立标准。
- 前端已选 openapi-typescript 从共同契约生成 TypeScript 类型，业务请求通过统一 Axios 实例调用；暂不默认生成完整请求 SDK。服务端允许手写实现，但必须通过共同契约验证。
- Java、Go 使用专门的接口 DTO 映射内部模型，避免直接暴露 ORM 实体、框架分页对象、异常类或语言特有类型。
- OpenAPI 版本、机器契约文件位置及契约校验工具在 M1 确定；前端已安装 openapi-typescript，具体版本见前端 package.json，生成配置待共同契约建立后验证。目前尚未创建 OpenAPI 文件、生成类型或客户端、接入 CI。

OpenAPI 是与语言无关的 HTTP API 描述规范，可用于文档、代码生成和测试；具体采用的版本应由所选工具链兼容性验证后确定，见 [OpenAPI 官方规范](https://spec.openapis.org/oas/v3.1.1.html)。

### Go 实现组织（已落实基础装配）

Go 采用显式路由注册：`internal/app/routes.go` 汇总路由；`internal/platform/httpserver/` 提供 Gin 引擎、公共中间件、健康检查及 HTTP 生命周期。后续业务 Handler、DTO 和路由注册位于对应业务模块的 `http/` 子包，Service 与 Repository 按实际用例增加，详见[技术栈规划](../技术栈规划.md#go-http-路由组织)。当前只开放健康检查，未注册本规划中的账号业务接口，也未确定全部共同契约。

## 三、HTTP 与数据格式（建议基线）

### 3.1 路径与方法

- 业务接口统一使用 `/api/v1` 前缀，资源路径采用小写复数名词，复合词使用连字符；路径不包含 Java、Go 或框架名称。
- `GET` 查询、`POST` 创建或提交动作、`PATCH` 部分修改、`PUT` 整体替换指定子资源、`DELETE` 删除。
- GET 请求不修改业务数据；登录、退出和修改密码使用明确的写接口。
- 列表查询使用查询参数，创建和修改使用 JSON 请求体；暂不引入 GraphQL、通用查询语言或批量接口。
- 修改接口逐字段定义允许修改的属性；客户端不能通过附加字段修改 ID、密码哈希、权限或审计字段。

### 3.2 JSON 与字段约定

| 项目 | 建议规则 |
| --- | --- |
| 媒体类型 | 普通请求响应使用 `application/json`；错误使用 `application/problem+json`；204 响应无正文 |
| 字段名 | 使用 `camelCase`，例如 `createdAt`、`pageSize` |
| ID | 对外统一为非空字符串，不要求采用特定 ID 生成算法 |
| 时间 | 时间点使用 UTC、固定毫秒精度，例如 `2026-10-20T08:30:00.000Z`；日期类字段另用 `YYYY-MM-DD` |
| 布尔值 | 使用 JSON `true`、`false`，不使用 `0/1` 或字符串替代 |
| 枚举 | 使用稳定的字符串值，并在契约中列举，不能直接暴露语言枚举序号 |
| 数组 | 无数据时返回 `[]`，不返回 `null`；必要的集合大小上限写入契约 |
| 缺失与 null | 请求字段是否必填、是否可为 null 分别声明；响应字段按 schema 返回，避免依赖序列化器默认省略规则 |
| 数值 | 分页与计数使用约束范围内的整数；未来涉及金额时另行定义精度与字符串表达规则 |
| 字符串校验 | 两种语言统一长度计算口径、大小写与空白处理；密码不自动 trim，账号、编码的唯一性规范在建模时确定 |

PATCH 请求中，字段缺失表示保持原值；显式 `null` 仅允许清空契约声明可空的字段；`false`、`0` 和空字符串不得被当作字段缺失。建议普通 JSON PATCH 请求体采用本项目明确的部分更新语义，不宣称实现 JSON Patch 或 JSON Merge Patch 标准。

建议拒绝写请求中的未知字段及未定义的业务查询参数，减少拼写错误和框架绑定差异；前端对新增响应字段保持兼容。各接口仍须明确字段长度、格式、重复查询参数及非法类型的处理规则，不能仅依赖框架默认行为。

### 3.3 分页、筛选与排序

| 参数或行为 | 建议规则 |
| --- | --- |
| 页码 | `page` 从 1 开始，默认 1 |
| 每页条数 | `pageSize` 默认 20，允许 1–100，超限返回 400，不静默截断 |
| 排序 | `sortBy` 与 `sortOrder`；后者为 `asc` 或 `desc`，字段使用白名单 |
| 默认顺序 | 列表默认 `createdAt desc, id desc`；自定义排序追加 ID 作为并列排序条件 |
| 筛选 | 按字段明确精确或模糊匹配、大小写及空值语义；不同接口不自动获得通用筛选能力 |
| 时间区间 | 审计查询采用 `occurredAtFrom` 包含起点、`occurredAtTo` 不包含终点，均使用统一 UTC 格式 |
| 越界页码 | 合法页码超出结果范围返回空 `items`，保留过滤后的 `total` |

稳定排序避免相同时间值导致顺序随机，但不保证并发增删时偏移分页具备快照一致性；第一期不默认引入游标分页。

## 四、响应与错误（建议基线）

### 4.1 成功响应

建议普通查询直接返回资源 DTO；列表返回统一分页对象，不额外叠加 `success/code/message/data` 成功包装。这样可以直接描述资源类型，并保持 HTTP 状态语义清晰。

列表请求示例：`GET /api/v1/example-records?page=1&pageSize=20`。

```json
{
  "items": [
    {
      "id": "10001",
      "code": "EXAMPLE-001",
      "name": "示例记录",
      "status": "enabled",
      "remark": null,
      "createdAt": "2026-10-20T08:30:00.000Z",
      "updatedAt": "2026-10-20T08:30:00.000Z"
    }
  ],
  "total": 1,
  "page": 1,
  "pageSize": 20
}
```

查询、修改成功建议返回 200 和资源 DTO；创建成功返回 201、资源 DTO 及 `Location`；删除、退出和成功修改密码返回 204，前端请求层须正确处理空正文。

### 4.2 错误响应

建议采用 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)，扩展稳定业务错误码 `code`、请求标识 `requestId`，参数校验错误可附带 `errors`。以下为 409 编码重复示例：

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "示例编码已存在",
  "code": "EXAMPLE_CODE_CONFLICT",
  "requestId": "example-request-id"
}
```

- 前端按 HTTP 状态和稳定 `code` 处理分支，提示文字可调整；`status` 必须与实际 HTTP 状态一致。
- 参数校验 `errors` 建议为数组，每项包含 `field`、`code`、`message`；不回显密码、Token 或完整敏感输入，也不依赖数组顺序。
- 响应通过 `X-Request-Id` 返回服务端生成或验证过的请求标识，错误正文中的值与之对应；它用于关联日志，不能作为身份凭据。
- 框架校验失败、鉴权失败及未处理异常均映射到相同错误契约，不返回堆栈、SQL 或框架内部错误对象。

| HTTP 状态 | 建议语义与示例 code |
| --- | --- |
| 400 | JSON 解析、参数类型、必填、长度或范围错误：`VALIDATION_FAILED` |
| 401 | 登录失败：`LOGIN_FAILED`；受保护接口缺少、过期或失效 Token：`AUTH_REQUIRED`、`TOKEN_INVALID` |
| 403 | 身份有效但缺少操作权限：`PERMISSION_DENIED` |
| 404 | 接口或有权查询的目标资源不存在：`RESOURCE_NOT_FOUND` |
| 409 | 唯一性冲突或状态冲突，例如 `EXAMPLE_CODE_CONFLICT`、`LAST_ADMIN_REQUIRED` |
| 429 | 登录失败限流等请求频率限制：`RATE_LIMITED`，明确重试时间及 `Retry-After` |
| 500 | 未预期的内部错误：`INTERNAL_ERROR`，不暴露内部原因 |

建议处理顺序为认证、接口授权、参数及资源处理；缺少接口权限先返回 403，避免通过错误差异探测资源。本人资料接口从认证上下文确定用户，不接收任意用户 ID。今后引入私有数据时，统一定义资源范围错误是否返回 404。

405、413、415 等协议层错误按实际语义处理，能够由应用处理的错误也使用统一正文；反向代理产生的错误需另行配置，前端保留非 JSON 错误兜底。HTTP 语义参考 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

## 运维端点与业务 API 边界

- Go 骨架已公开 GET /health/live 和 GET /health/ready，后者检查数据库并在不可用时返回 503，仅返回 up/down；Java 仍使用 /actuator/health。它们是各自的运维端点，不确定共同业务 API。Go 未注册请求目前返回 403，不代表已实现本文的认证、授权或错误契约。

## 五、契约验证与实施顺序

### 5.1 共用用例，分别验收

维护一组只依赖 HTTP、可配置后端地址和测试账号的验收场景，分别在 Java、Go 的独立环境执行，不要求两个后端同时运行或连接相同数据库。

| 类别 | 验证内容 |
| --- | --- |
| 结构 | 状态码、媒体类型、响应头、字段类型、必填、可空、空数组、204 空正文 |
| 边界 | 缺失、null、false、0、空字符串、非法枚举、超大分页、未知字段和重复编码 |
| 业务 | 创建后查询、修改后持久化、删除后不存在、角色关联替换与分页筛选结果 |
| 安全 | 未登录、越权读写、本人资料篡改、Token 到期及撤销、禁用与密码变更、及时撤权和最后管理员保护 |
| 前端 | 同一套页面与请求代码在各自环境完成登录、权限展示、CRUD、审计及错误处理 |

用例基于各环境受控初始化数据断言语义，不逐字比较动态生成的 ID、时间、Token 和请求标识。契约 schema 验证不能替代状态变化及安全场景测试。管理员保护还须覆盖并发撤权、禁用等可能破坏不变量的情况。

### 5.2 最小落地顺序

1. 确定本文建议基线中的格式、Token 关键决策及 OpenAPI 工具链，更新相关规划中的状态。
2. 先补齐登录、退出、当前用户及示例记录 CRUD 的机器契约、样例和权限定义。
3. Java、Go 各自实现最小链路，用同一组场景独立验收，再复用前端完成联调。
4. 扩展用户、角色、授权及审计契约；接入契约校验、相同场景和前端构建验证。
5. 后续接口变更先修改共同契约与场景，再同步两套模板及前端；记录各实现的完成状态，不能用一套通过替代全部交付。

### 5.3 版本与派生项目维护

- 建议 `/api/v1` 表示对外契约主版本；契约文件自身版本和模板提交另行记录，不能将某个后端版本号当作共同 API 版本。
- 字段删除、类型改变、新增请求必填项、认证或状态码语义改变均需评估破坏性；新增响应字段也需验证客户端兼容，新增枚举值不自动视为安全变更。
- 模板契约演进需同步两种实现；派生项目按自身需求独立维护 API，记录来源提交，公共修复和契约变更不会自动传播到既有项目。
