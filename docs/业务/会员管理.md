## 普通会员表 `member_user`

按本次用户要求，先完整保留 `MemberUserDO` 显式声明的全部字段，并增加 `username`；调整名称或类型，不省略业务字段。原基类源码未提供，现有实体只有显式审计字段，不猜测其他继承字段；后续租户归属见[多租户](多租户.md)。管理端账号不天然等于超级管理员，其权限由 RBAC 决定；会员与管理端是独立身份，未来会话不得仅凭数值用户 ID 混用。

### 完整实体的边界

- 本轮根据用户要求预留完整会员数据，不把积分、等级、分组等规划字段视为第一期已经可用的能力；也不增加会员 API 或修改既有管理端契约。
- 标签暂采用 jsonb，以保留单表实体中的 `TagIDs` 集合，不保存逗号拼接 ID。写入前应去重、检查正整数并规范为空数组；不得写 JSON null。数据库约束尚未实现。jsonb 无法逐项建立标签外键，真正实现标签管理和关联检索时应评估迁移为会员标签关联表，避免同时维护两份关系来源。
- 积分与经验后续建议增加非负约束（允许负积分时须明确调整规则），通过服务层事务和原子更新处理；需要积分流水、幂等与扣减规则后才能开放操作。参考代码中的 `totalPoint` 仅为 TODO，没有既定统计口径，本轮不额外创建该字段。
- 默认会员名、手机邮箱校验、注册终端编码、标签数量上限、等级与分组关系均待功能实现前确定。实体标签不是校验器，会员不能通过资料更新接口直接修改积分、经验、等级、分组和标签等受控字段。
- `created_by`、`updated_by` 无法独立表达两种账号体系的全部操作者；后续审计需显式区分管理端与会员身份，不能给这两个字段直接建立到会员表的自引用外键。
