## F02 登录、会话与个人中心

实现内容：

- 用户名与密码登录、退出、当前用户信息查询、登录过期处理，以及基础的登录失败限流。
- Redis 已纳入技术栈，规划承载多实例共享限流；算法、阈值、TTL 和故障行为待登录业务实现前确定，目前没有 Redis 或限流实现。引入 Redis 不改变既定的会话失效与及时撤权规则，具体技术边界见[技术栈规划](../技术栈规划.md)。
- 按 Token 方向设计登录凭据签发、请求校验与失效处理；本文中的 Session/会话仅表示一次独立登录交互，不指框架 HttpSession、Cookie Session 或通用状态容器；登录有效性由 JWT 校验与 Redis 记录共同判定。
- 密码使用安全的单向哈希存储，接口不返回密码哈希；不在日志中记录密码或登录凭据。
- 个人中心支持修改昵称和本人密码；修改密码验证原密码，账号身份以服务端认证结果为准。
- 退出后当前会话失效；账号禁用后旧会话不可继续访问受保护接口；密码修改或重置后所有旧会话失效，要求重新登录。
- 角色或权限变更后，下一次受保护请求按最新有效权限判定，不能一直沿用登录时的授权结果。

验收：分别验证正确登录、错误登录、退出、过期、禁用和密码变更；原凭据在对应失效条件下不可继续使用；篡改用户 ID 无法修改他人资料或密码。

## 账号管理与登录凭据

### 一、已确定的规则与术语

- 登录凭据采用 JWT，通过 `Authorization: Bearer` 传递；Redis 保存每枚 JWT 对应的有效记录。此方向替换此前“不透明 Token + PostgreSQL 登录记录”，目前仅为设计，尚无认证代码。
- Session/会话在这里仅表示一次独立登录交互，不指 Java HttpSession 或 Cookie Session。服务端仍需在 Redis 管理登录有效性，不能把该方案称作完全无服务端状态。
- 普通会员允许同账号多端同时登录；每次登录独立签发 JWT，使用独立 jti，新登录不覆盖已有有效记录。同一设备重复登录的合并或数量上限尚未确定。
- 单次登出仅撤销当前 JWT 对应记录，其他登录不受影响；某枚 JWT 到期也只影响该枚凭据。账号禁用、修改/重置密码使该账号全部旧凭据失效；租户禁用按租户范围失效，重新启用不能恢复旧凭据。
- 账号级撤销以租户、身份类型和账号共同限定；管理端账号与同名或同 ID 的会员不是同一主体，不得误撤销其他身份或租户的登录。
- 这些多端规则目前只确定用于普通会员，管理端多端策略仍待讨论。新增公开注册尚未确定，不能把已有会员实体视为已经开放注册。

### 二、JWT 与 jti 的关系

jti 是 JWT ID，服务端签发前生成并放入载荷，随后签名；不是对签名后的 JWT 再补充字段。同一用户每次登录使用不同 jti。以下仅展示候选字段，不是可用凭据或已完成的机器契约：

```json
{
  "iss": "configured-issuer",
  "aud": "member-api",
  "sub": "1001",
  "tenantId": "10",
  "userType": "member",
  "jti": "server-generated-unique-id",
  "authVersion": 1,
  "iat": 0,
  "exp": 0
}
```

`sub` 表示账号，`jti` 标识这枚凭据，`authVersion` 是本项目自定义的签发时账号凭据版本；租户和身份类型共同明确归属。签发者、受众和算法的具体值待选型。先验证算法白名单、签名、时间及必须声明，再信任载荷，不能只 Base64 解码就查询并授权。JWT 不放密码或敏感资料，不作为当前角色权限的唯一来源。依据：[JWT 声明](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1)、[JWT 安全实践](https://www.rfc-editor.org/rfc/rfc8725.html)。

### 三、Redis 记录草案

建议以 jti 作为 Key 的一部分，示例：

```text
{application}:{environment}:auth:member:tenant:{tenantId}:token:{jti}
```

Value 建议保存账号 ID、租户、身份类型、到期时间、JWT 摘要等必要元数据，不保存可直接使用的 JWT 原文；具体格式仍待实现前确认。平台身份采用独立范围，不用租户 0 或空值冒充平台。

- 登录时创建有效记录并设置过期，写入成功才返回 JWT；失败不返回可用凭据。Key 与过期设置须原子执行。
- 过期时间与 JWT 的 exp 对齐，不能只延长 Redis TTL 就延长 JWT。若将来启用刷新，须重新签发并定义旧凭据与 jti 的轮换规则。依据：[Redis 过期机制](https://redis.io/docs/latest/commands/expire/)。
- 每次请求校验 JWT，再核对 Redis 记录与载荷的身份归属、到期和摘要（采用时），同时读取数据库中当前账号 auth_version、账号/租户状态及有效权限；JWT authVersion 必须与数据库版本相等。
- 记录缺失、过期或不匹配视为未认证，不能从 JWT 自动补回记录；Redis 不可用拒绝认证处理，建议返回 503，不能退化为仅验签通过。
- 当前凭据登出按已验证的 jti 删除准确 Key，服务端撤销成功才报告登出成功。客户端清理凭据不能代替服务端撤销；重复登出与无效凭据的完整 HTTP 语义待共同契约确定。
- 改密与重置密码后的全账号失效采用数据库 auth_version，不依赖扫描或批量删除 Redis。用户到 jti 的索引仅作为后续登录管理和物理清理的候选，不作为此次版本判定的必要条件；采用时须包含租户和身份并清理到期成员。

### 四、账号凭据版本 auth_version

此项已确定用于账号级旧凭据失效，Go 管理账号与会员实体已加入 AuthVersion 字段；迁移、版本递增与认证比较尚未实现。

| 位置 | 字段 | 规则 |
| --- | --- | --- |
| 管理账号和会员表 | `auth_version bigint NOT NULL DEFAULT 1` | Go 使用 int64；值为正整数，单调递增，不重置或回退；不是普通资料更新字段 |
| JWT | `authVersion` | 自定义载荷字段，记录与已验证密码哈希一起读取的账号版本；必须存在且类型和值合法 |
| Redis | 可附带版本元数据 | 用于一致性核对；不能代替读取数据库当前版本，也不能只比较两个旧版本 |

- 登录：从同一账号快照读取密码哈希与 auth_version，验证该哈希后用配套版本签发 JWT。禁止验证旧密码后再读取新版本并写入 JWT，否则并发改密时可能签出仍有效的凭据。
- 请求：按已验证 JWT 的租户、身份类型和账号定位数据库记录，严格比较 authVersion 与当前 auth_version；缺失、非法或不相等按未认证处理，建议返回 401。首期直接查数据库，不从滞后的 Redis 或本地缓存取得当前版本。
- 修改或重置密码：在同一个 PostgreSQL 事务内更新 password_hash，并原子执行 `auth_version = auth_version + 1`，成功审计按既有要求加入该事务；失败时整体回滚，不能先改密码再用独立事务递增。采用锁或条件更新协调并发改密，防止校验旧快照后覆盖更新，具体 SQL 随实现确定。
- 提交后的后续认证检查会拒绝全部旧版本 JWT，包括当前端；已经完成认证并正在执行的请求不会自动被回滚，敏感写操作是否在事务内再次检查凭据版本，随用例明确。
- 单次登录、单次登出与单枚 Token 到期不增加 auth_version。当前登出仍仅删除对应 jti，保留其他正常登录。
- 改密后 Redis 旧记录即使暂未删除，也因版本不匹配不能通过认证；可等待 TTL 或异步清理。Redis 清理失败不撤销已提交的新密码及版本，也不能让旧凭据重新有效。
- 版本只限定同租户、同身份的同一个账号，不用于角色权限版本、JWT 密钥版本或全局租户失效；禁用/重新启用与租户级失效的版本协调另行细化。

### 五、跨存储与故障边界

账号与密码哈希仍在 PostgreSQL，登录有效记录在 Redis；二者没有同一个本地事务。登录与改密/禁用并发时，不能让使用旧密码验证的请求在撤销后新建有效记录。改密与重置密码采用上述 auth_version 作为持久化失效依据；旧快照签发的 JWT 必须携带旧版本，后续认证因此失败。账号/租户禁用和重新启用的并发处理、Redis 单次登出失败或恢复等机制仍须细化与验证，不能把账号版本视为所有故障的通用解法。

Redis 登录记录被丢弃会导致重新登录；恢复旧快照或故障切换也不能让已撤销凭据复活。容量隔离、持久化、高可用和恢复时的整批失效策略待部署设计。JWT 登录记录属于认证状态，与可回源重建的普通缓存区别对待。

### 六、注册、改密与后续待定项

- 管理端账号由管理员创建、会员允许自行注册、注册后不自动登录等仍是此前讨论建议，尚未确认；租户开通与会员注册也不是同一用例。
- 已有改密要求保留：本人登录后验证原密码，成功后全部旧凭据失效；管理员重置密码独立授权，不能通过资料更新接口直接改哈希。
- 待定：注册开放范围与参数、用户名/密码完整校验、JWT 库和签名算法、密钥轮换、有效期、前端存储、刷新机制、管理端多端策略、会员登录数量上限、可选登录索引、并发改密 SQL、禁用与租户级撤销、Redis 恢复和依赖故障语义；改密使用 auth_version 已确定。
- 最小验证覆盖：会员两次登录同时有效，退出 A 后 B 可用，A 过期不影响 B，改密/重置后全部旧版本失效、新密码登录获得新版本，改密事务失败保持旧密码与版本不变，缺失/非法版本被拒绝，验证旧密码的并发登录不能携新版本通过，Redis 清理失败仍拒绝旧版本，禁用后旧凭据失效，伪造 jti/签名/租户/身份被拒绝，Redis 缺失与故障不放行，角色撤销下一次请求生效；跨存储失败、并发及恢复场景随机制一并验证。Java、Go 分别满足共同规则。
