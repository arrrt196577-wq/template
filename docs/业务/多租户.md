## 多租户业务与隔离

- 创建日期：2026-10-21（Asia/Hong_Kong）。
- 需求状态：用户已明确后续支持多租户，本轮先完成设计。
- 实现状态：现有 `AdminUser`、`MemberUser` 没有租户字段；租户表、上下文、查询隔离和测试均未实现，不能宣称可用于多租户部署。
- 方案状态：以下为建议基线，隔离方式、账号归属及平台账号模型待确认后落实到代码、迁移与共同契约。
- 相关文档：[数据模型与实体规划](用户管理.md#数据模型与实体规划)、[API 规划](../接口/公共规范.md)、[业务范围与阶段](业务范围与阶段.md#业务范围与阶段)、[技术栈规划](../技术栈规划.md)。

### 一、隔离方式与数据归属

建议采用 PostgreSQL 共享库共享表，使用非空 `tenant_id` 隔离租户数据，沿用现有单应用与数据库工具，减少逐租户迁移和连接管理成本。如果需要租户独立备份恢复、专属部署或更强的物理隔离，需改评估独立数据库方案；这些需求目前不确定。

| 数据 | 建议范围 | 说明 |
| --- | --- | --- |
| 租户目录 `tenant` | 平台 | 租户信息、可用状态 |
| 平台账号 `platform_user`（候选） | 平台 | 独立身份，不混入租户账号表 |
| `admin_user` | 租户 | 管理端账号，超级管理员角色也仅在本租户生效 |
| `member_user` | 租户 | 普通会员，与管理端是不同身份 |
| 员工、部门、岗位及员工岗位关系 | 租户 | [员工基础字段与规则](员工管理.md)已认可；组织配套结构待补齐，关联必须同租户，尚未实现 |
| 角色、用户角色、角色权限、示例记录 | 租户 | 授权和业务资源都必须隔离 |
| 会员等级、标签、分组、积分流水（后续） | 租户 | 关联目标必须属于同一租户 |
| 权限标识目录、明确的公共地区字典 | 平台公共 | 权限目录公共不代表角色授权公共；地区字典范围待定 |
| 会话、审计 | 按身份区分 | 租户会话和事件包含租户，平台范围独立定义 |

建议一条管理账号或会员记录只属于一个租户。同一自然人跨租户使用独立账号、凭据和资料。如果要全局账号加入多个租户，应采用全局身份加租户成员关系，不能仅给当前用户表加字段。

本轮提前规划数据与身份边界；套餐、计费、域名管理、自助开通、跨租户数据搬迁不自动纳入首期功能。

### 二、表结构与完整性

#### 2.1 租户表 `tenant`（草案）

| 字段 | 建议类型 | 规则 |
| --- | --- | --- |
| `id` | `bigint` identity | 主键 |
| `code` | `varchar(64)` | 非空、全局唯一、规范化，建议创建后不变；登录选择租户的候选标识 |
| `name` | `varchar(128)` | 非空，展示名称 |
| `status` | `varchar(16)` | `enabled`、`disabled`，默认启用 |
| `created_at`、`updated_at` | `timestamptz(3)` | 非空，更新时显式维护 |

暂不增加套餐或到期时间；新增到期机制时再定义访问和会话失效行为。停用租户不级联删除账号、业务数据和审计。

#### 2.2 账号与关联表调整方向

- `admin_user`、`member_user` 新增 `tenant_id bigint NOT NULL`，引用 `tenant.id`。禁止默认租户，不用 0 或 NULL 表示平台账号；普通更新不能修改归属。
- 保留全表唯一 `id` 主键，同时增加 `UNIQUE (tenant_id, id)`，供关联表的复合外键引用。
- 用户名改为 `UNIQUE (tenant_id, username)`，两个账号表各自约束；跨租户可同名。手机邮箱是否用于登录、如何规范化与租户内唯一，另行确定。
- 角色编码、示例编码等采用租户内唯一约束。列表索引建议按查询增加 `(tenant_id, created_at DESC, id DESC)`，替换原无租户索引草案。
- 用户角色表同时用 `(tenant_id, user_id)`、`(tenant_id, role_id)` 引用同租户的用户与角色；会员等级、分组关系同理。只关联 `id` 只能证明记录存在，不能保证租户一致。PostgreSQL 支持多列唯一约束与外键，见[官方约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html)。
- 会员 `TagIDs` 当前为 JSONB，无法逐项建立复合外键；后续写入须验证每个标签归属。正式启用标签管理时建议迁移到含 `tenant_id` 的关联表，将 `TagIDs` 作为查询投影，避免两份持久化关系来源。
- `created_by`、`updated_by` 先保留，写入用例须明确其身份范围，不能混写平台、管理端与会员 ID。审计应表达操作者类型、ID、资源租户；平台跨租户操作另记录平台身份，不能冒充租户用户。

### 三、登录与会话

1. 登录前确定目标租户，建议共同契约增加 `tenantCode`，域名映射为候选替代；具体入口与字段待定。租户标识是选择目标，不是凭据。
2. 账号查询同时限定租户、用户名和身份体系，检查租户及账号状态；管理端与会员登录入口区分。失败提示避免泄露账号存在性，限流考虑来源 IP 与租户账号组合。
3. JWT 与 Redis 有效记录绑定账号、租户和身份类型，每次登录生成独立 jti；管理端与会员记录采用区分身份的 Key 范围，不再规划独立数据库会话表。客户端仍把 JWT 当作不透明凭据。
4. 受保护请求从已验证会话建立服务端租户上下文，客户端请求头、路径或正文不能覆盖它；若仍传租户标识，必须与会话一致，否则拒绝。
5. 每次请求检查租户状态、会话、账号及最新权限。缺失上下文必须拒绝租户业务访问，不能降级为全表查询或默认租户。
6. 切换租户建议重新认证并签发目标会话；不能修改请求头直接切换。若采用全局成员模型则另设计切换授权。
7. 禁用租户后后续租户请求拒绝，并撤销全部旧会话；重新启用不恢复旧会话。并发登录与禁用须协调事务或锁，具体机制待实现设计。

授权必须同时检查身份范围、同租户、接口权限和本人或其他数据范围。最后一个可用管理员保护按租户分别计算，平台管理员另行定义；租户超级管理员不能跳过租户过滤。

### 四、查询与平台管理

- Repository 要求显式租户范围或受控的租户实例。列表、总数、详情、更新、删除、关联及原生 SQL 都限定租户；INSERT 归属由服务端赋值，UPDATE 不得改变归属。
- 结构体标签、嵌入、通用 ORM 回调与前端筛选均不等于完整隔离；公共封装也须覆盖跨租户验证。
- 已有接口权限但资源属于其他租户时，建议返回 404，避免暴露其存在性；共同契约落实时确认错误语义。
- 平台入口、身份、权限与 Repository 能力独立。禁止“超级管理员自动忽略租户”或客户端可传的 `skipTenant`；跨租户操作明确指定目标、授权并审计。
- 后台任务、批处理与业务管理命令显式建立租户范围。未来缓存键、文件路径、幂等键、导出任务和消息负载都纳入租户与身份范围。
- PostgreSQL RLS 可作数据库侧补充防护候选，尚未选定或实现。若采用，验证表所有者和 BYPASSRLS 绕过行为，以及连接池租户上下文复用，不能仅设置连接级变量就假定安全。见[官方行级安全文档](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)。

### 五、Go 字段复用方向

建议在 `internal/platform/persistence/` 分别定义 `AuditFields`、`TenantFields`，由业务 `postgres` 适配包按需嵌入，业务根包继续不依赖 GORM。分开定义，避免平台账号、租户目录、公共字典被迫携带租户字段。

```go
// 设计示意，尚未加入实际代码。
type TenantFields struct {
    TenantID int64 `gorm:"column:tenant_id;type:bigint;not null;<-:create"`
}

type AdminUser struct {
    TenantFields
    AuditFields
    // 账号与资料字段……
}
```

嵌入只复用字段映射，不生成安全边界。租户字段无默认值，后续必须校验有效性并落实外键；认证上下文与查询隔离另行实现。

### 六、实施与验收顺序

1. 确认隔离方式、账号归属及平台账号模型；补齐 Java、Go 与前端共用的登录和会话租户契约。
2. 编写租户与账号迁移，调整现有实体公共字段与租户字段。当前无业务表，可在首个迁移前按确认方案设计；已有数据的派生项目需单独回填、查重、再收紧约束，不能直接套默认租户。
3. 实现上下文、租户限定 Repository、身份分流、会话与事务约束，再开放业务接口。
4. 至少使用两个租户验证：同名登录、伪造租户、Token 租户不一致、跨租户详情/列表总数/写操作、跨租户角色及会员关联、租户禁用与重启用、平台越权和各租户最后管理员保护；后台任务、缓存等在引入时补测。
5. Java、Go 分别通过相同隔离场景，不能用一套或一个默认租户通过代替完整验收。

本轮仅修改规划，不修改 Go 实体和运行接口，也不执行数据库迁移。实际多租户交付范围与阶段在方案确认后细化。

### 七、需要确认的产品边界

1. 共享库共享表是否满足要求，是否需要客户独立备份恢复或专属部署。
2. 一个账号只属于一个租户，还是全局账号可以加入多个租户。
3. 平台是否采用独立账号体系；登录用租户编码还是域名选租户。
