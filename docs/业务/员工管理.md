## 一、范围与建模边界

`employee` 保存员工当前档案、任职信息及管理账号关联，不承担登录凭据或权限管理。员工可以没有管理账号，管理账号也不必对应员工；不与会员身份自动合并。

本版采用一个主部门、可有多个岗位的基础模型。主部门存于员工表，岗位通过独立的 `employee_position` 关联，不保存岗位 ID 的 JSON 数组。配套 `department`、`position` 及关联表的完整字段、层级规则与迁移需后续设计，不能直接据本版执行整套组织建表。

当前仅规划基础在职与离职，不自动加入第一期必做范围；待入职、试用期、跨部门兼任、返聘及其历史模型尚未确定。多租户物理隔离继续遵循[多租户规划](多租户.md)的状态，本版租户字段按共享表基线记录，不代表整体隔离方案已实现或全部定稿。

## 二、员工表 `employee`

“必填”表示数据库非空，不表示客户端可以提交；类型及默认值作为本版建表基线，物理约束与索引集中维护于[数据库表规划](../数据库表规划.md#四物理结构与约束规划)。

| 字段 | PostgreSQL 类型 | 必填 | 默认值 | 含义与规则 |
| --- | --- | --- | --- | --- |
| `id` | `bigint GENERATED ALWAYS AS IDENTITY` | 是 | 数据库生成 | 员工主键，不使用工号作为主键 |
| `tenant_id` | `bigint` | 是 | 无 | 所属租户，由服务端赋值，普通编辑不可修改 |
| `employee_no` | `varchar(64)` | 是 | 无 | 工号，租户内唯一；离职后不释放、不复用 |
| `name` | `varchar(64)` | 是 | 无 | 员工姓名，不唯一，禁止空白 |
| `department_id` | `bigint` | 否 | `NULL` | 当前主部门，允许暂未分配，关联目标必须同租户 |
| `admin_user_id` | `bigint` | 否 | `NULL` | 可选管理端账号，同租户一对一；不是员工登录凭据 |
| `mobile` | `varchar(32)` | 否 | `NULL` | 员工联系电话，不默认作为登录标识，不要求唯一 |
| `email` | `varchar(254)` | 否 | `NULL` | 员工联系邮箱，不默认作为登录标识，不要求唯一 |
| `employment_status` | `varchar(16)` | 是 | 无 | `employed`（在职）、`departed`（离职），由入职、离职流程写入 |
| `hired_on` | `date` | 是 | 无 | 本次任职的入职日期，按日历日期处理 |
| `left_on` | `date` | 否 | `NULL` | 本次任职的离职日期；在职为空，离职必填且不早于入职日期 |
| `remark` | `varchar(500)` | 否 | `NULL` | 员工管理备注，不存凭据或额外敏感档案 |
| `created_at` | `timestamptz(3)` | 是 | `CURRENT_TIMESTAMP` | 创建时间，写入后不可修改 |
| `updated_at` | `timestamptz(3)` | 是 | `CURRENT_TIMESTAMP` | 更新时间，应用显式维护，默认值不会随 UPDATE 自动更新 |
| `created_by` | `bigint` | 否 | `NULL` | 创建管理账号 ID；系统初始化可为空 |
| `updated_by` | `bigint` | 否 | `NULL` | 最近修改管理账号 ID；系统操作可为空 |

## 三、业务与写入规则

### 3.1 资料与关联

- 工号租户内唯一，离职不释放；建议去首尾空白并统一 ASCII 字母大小写，具体字符范围及规范化方向在接口契约中细化，数据库约束须与应用一致。
- 员工姓名与账号昵称语义不同；员工联系方式以员工档案为准，不自动与账号资料双向同步。可选文本建议将空串或全空白规范为 `NULL`，长度与格式校验在两套后端保持一致。
- 同一管理账号最多关联一个员工，多个员工可以不绑定账号；部门和账号关联必须属于员工所在租户。
- 岗位不是权限角色，不因员工入职、调部门或分配岗位自动授予角色；授权继续通过[角色与权限](角色与权限.md)控制。
- 账号绑定、解绑、入离职为受控操作，不能通过通用资料编辑任意修改。客户端不得修改租户、主键、创建审计字段，后端按白名单写入。
- `created_by`、`updated_by` 只解释为管理端账号 ID，平台身份与会员 ID 不混写；平台操作通过[审计](审计.md)记录实际身份。操作者外键仍需结合身份边界定稿。

### 3.2 入职、离职与历史

- 在职时离职日期为空；离职时离职日期必填且不早于本次入职日期。任职状态与日期由服务端流程一致写入，不由资料编辑独立切换。
- 员工状态与账号启停状态分开。离职流程须处理关联账号禁用和旧凭据失效，不能只更新员工状态；同时遵守最后一个可用管理员保护，无法完成时不得留下部分离职结果。
- 员工、账号变更与成功审计应在 PostgreSQL 同事务处理；Redis 撤销不能加入数据库事务，具体失效和并发机制按[认证与个人中心](认证与个人中心.md)、[用户管理](用户管理.md)继续细化，当前未实现。
- 当前表只表达当前任职，不保存多次入离职或调动历史。开放返聘或历史查询前先设计任职历史，不能直接覆盖日期丢失历史，也不能仅用操作审计替代业务历史；重新入职不自动恢复原账号权限。
- 本版不增加通用 `status`、逻辑删除字段或员工删除能力，离职保留档案。

## 四、暂不纳入与待定事项

- 性别、生日、头像按实际展示需要再加；身份证、住址、银行卡、薪资、考勤和合同不提前纳入基础员工表。
- 待入职、试用期、未来生效的入离职、跨部门兼任、返聘与历史查询的需求及日期生效口径待确认，不根据日期自行推导认证是否有效。
- 部门、岗位与员工岗位关联表完整设计，以及账号绑定/解绑、离职后绑定与账号启用的规则需在开放功能前补齐，避免绕过离职停用要求。
- 员工模块 API 路径、DTO、权限码、数据访问范围与交付阶段尚未确定；开发前新增对应接口规划并落实共同契约，Java、Go 与前端同步实施。

## 五、后续验收要求

以下为待实现的验收要求，不代表已执行测试：

- [ ] 员工无账号、无部门时可按规则创建；同租户工号并发重复仅一个成功，离职后仍不能复用。
- [ ] 同一账号不能关联多个员工；多个未绑定员工可同时存在，跨租户部门与账号关联被拒绝。
- [ ] 状态及日期非法组合被数据库与服务端拒绝；日期映射不因时区发生偏移。
- [ ] 员工、账号资料不会意外双向覆盖；部门、岗位变更不会自动增加权限。
- [ ] 离职成功后关联账号后续请求被拒绝，最后管理员保护及失败回滚有效，并发认证和离职场景另有针对性验证。
- [ ] 工号、账号关联、任职状态与审计字段的写入边界有效；无权限或跨租户访问被拒绝。
- [ ] Java、Go 分别通过共同契约及相同业务验收场景。
