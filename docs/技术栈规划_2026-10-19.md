## 目标与适用范围

为后续 Web 管理后台项目提供可复用的前后端基础工程，减少登录、权限、管理页面及工程配置的重复开发工作。

根据后续项目按语言选用后端的需求，分别开发 Java 与 Go 两套完整后端模板，复用一套 Vue 管理端模板和接口契约。每个派生项目只选择其中一套后端；本规划不设计同一项目内的双后端部署、运行时切换或按语言拆分业务职责。

选型优先考虑维护成本、实际复用需求、依赖兼容性和本地启动便利性。具体业务规则由派生项目实现，通用能力经过实际验证后再沉淀。

## 已确定的数据库方案

- Java、Go 两套后端统一使用 PostgreSQL 作为主数据库，模板不同时维护 MySQL 兼容实现。
- 选型理由：满足管理后台的关系数据、事务与查询需求，统一数据库以减少两套后端在数据库适配、迁移和验收上的维护成本。
- 统一数据库类型不代表共享运行数据；两套后端仍在各自独立的验收环境中验证，派生项目独立管理数据库和登录状态。
- PostgreSQL 具体版本、Go 数据访问及迁移工具，以及数据库结构和迁移脚本的复用边界仍待确定。
- Java 已引入 MyBatis-Plus、PostgreSQL JDBC、Flyway 及分页支持，并提供数据源环境变量配置；尚无业务表、迁移 SQL、Mapper 或持久化业务，未完成真实数据库联调。

### Java 持久层约定

- 选择 MyBatis-Plus 的理由：第一期主要是管理后台 CRUD，可减少重复代码；角色权限等关联查询仍可用 MyBatis XML 明确维护 SQL。当前不同时接入 JPA，也不重复引入 MyBatis starter。
- MyBatis-Plus 在父 POM 通过 BOM 固定为 3.5.17，使用 `mybatis-plus-spring-boot4-starter`；分页使用同版本 `mybatis-plus-jsqlparser` 和 PostgreSQL 方言拦截器。分页大小、排序白名单仍须在接口层校验，插件不替代授权检查。
- Flyway、PostgreSQL JDBC 和传递引入的 JDBC/HikariCP 版本由 Boot 管理。Boot 4 使用 `spring-boot-starter-flyway`，同时引入 `flyway-database-postgresql`，避免只有核心依赖却未启用自动迁移。
- 正常启动必须提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`；连接或迁移失败应阻止启动，不静默降级为无数据库模式。具体命令见 Java README。
- 迁移脚本由 app 的 `src/main/resources/db/migration/` 管理，按 `V1__description.sql` 等命名。结构变更只走版本化 SQL；已执行脚本不修改，新增脚本演进。关闭 SQL 初始化、自动 baseline 与 clean，保留迁移校验。当前仅建立目录说明，不创建占位业务迁移或默认管理员。
- 请求 DTO、响应 DTO 与数据库实体分离；事务放在业务 Service 层。不预建通用 CRUD Controller/Service，不默认开启逻辑删除、多租户或数据权限插件。具体 Mapper 随业务建立并标注 `@Mapper`，不扫描所有接口。
- Java 与 Go 只复用已经明确的契约和验收语义；不因 Java 选择 Flyway 就确定 Go 工具或迁移脚本复用方式。
- 依据：[MyBatis-Plus 安装](https://baomidou.com/getting-started/install/)、[分页插件](https://baomidou.com/plugins/pagination/)、[Boot 数据库初始化](https://docs.spring.io/spring-boot/4.1/how-to/data-initialization.html)、[Flyway PostgreSQL 支持](https://documentation.red-gate.com/fd/postgresql-database-277579325.html)。

- 版本和环境依据同时参考 [Boot 系统要求](https://docs.spring.io/spring-boot/4.1/system-requirements.html)及 [Maven 发布说明](https://maven.apache.org/download.cgi)。实际版本入口为 [Java 父 POM](../backend-template/java/pom.xml)和 Wrapper 配置。

| Maven 模块 | 职责与当前内容 |
| --- | --- |
| template-common | 不依赖 Spring，预留公共错误与分页类型包，尚无实现 |
| template-framework | 依赖 common，引入 MVC、Validation、Security、Actuator、默认日志及配置元数据处理器，包含默认拒绝的安全配置 |

模块用于一个应用内的职责分离，不代表服务拆分。预留包用 `package-info.java` 说明边界，不添加空 Controller、Service 或 Repository；业务代码出现后再按实际需要细分子包。

当前只开放 `GET /actuator/health`；其他请求拒绝，不生成默认用户或密码，也不创建认证会话。Spring Security 的引入仅确定安全基础组件，Token 登录、撤销、权限判定及 API 错误映射仍未实现；Java 已补齐 PostgreSQL 持久层依赖与配置，尚无业务持久化。运行与依赖说明见 Java 后端 README。

### 使用边界

- Pinia 仅保存必要的跨页面状态；列表数据、筛选表单和弹窗状态优先留在页面或 composable 中，避免把所有接口数据放进全局 store。
- 路由与菜单使用代码维护的静态定义，根据后端返回的有效权限过滤；页面守卫、菜单或按钮隐藏不替代服务端授权。
- API 类型由共同契约生成，业务请求通过统一 Axios 实例调用；本次仅确定类型生成工具，不默认生成完整请求 SDK。TypeScript 类型检查不等于运行时响应校验。
- 先沉淀分页、权限判断和错误处理等小型复用能力；通用 CRUD 页面抽象在真实复用需求明确后提炼。
- 选择 Pinia 不代表持久化 Token，不默认引入状态持久化插件。Token 前端存储、刷新页面后的登录体验及刷新机制仍须与鉴权方案一起确定。
- 前端已提供类型检查、构建、代码与格式检查及应用挂载冒烟用例；Vitest 已配置但尚无单元用例，业务与安全测试随实际功能补充。可执行命令见前端 README。

4. 前端固定 Node.js 24.22.0、pnpm 11.25.0，直接依赖使用精确版本并提交 `pnpm-lock.yaml`；后续升级验证 Vue、Vite、TypeScript、Element Plus、Sass 和测试工具的兼容组合。TypeScript 暂使用与 openapi-typescript peer 要求兼容的 5.9.3，不仅按最新版本选型。
5. 模板优先采用仍在维护的正式版本；依赖升级时检查兼容性，并验证受影响的启动、构建和功能链路。

前端实际版本以 package.json、锁文件及 `.node-version` 为准；Java 以父 POM 和 Wrapper 配置为准；Go 不填写未经确定的版本号，避免将候选版本误记为项目基线。

## 双后端目录与契约（规划）

共同接口及 Token 交互的建议基线见 [API 规划](API规划_2026-10-20.md)。前端 HTTP 与类型生成工具已在本文确定；具体路径、格式、OpenAPI 版本及契约校验工具仍需在开发前确定。

- `backend-template/` 保留为后端模板区域，`java/` 已建立三模块基础骨架；`go/` 尚未创建。
- 两套后端分别维护依赖、配置、数据迁移、测试与启动部署说明，均覆盖第一期规定的服务端能力。
- 先定义共同接口契约，包括路径与方法、认证交互、请求响应字段及类型、HTTP 状态码、错误语义、分页排序、时间格式和权限标识；具体格式及契约工具待定。
- 两套后端遵循相同的会话撤销、授权变更生效、本人数据边界及管理员保护规则；使用同一组契约与安全验收场景分别验证。
- 派生项目复制前端模板后，仅对接该项目所选后端；模板复用相同业务页面与请求代码，避免按语言编写响应解析分支。模板验收分别在独立环境中验证两种前后端组合。
- 两套后端统一使用 PostgreSQL，数据访问及迁移工具可按语言分别选型；数据库结构、迁移脚本等开发资产的复用边界待设计。各派生项目独立管理数据库和登录状态，不要求 Java、Go 之间互认 Token 或共享会话。

## 鉴权方向与待定事项

- 当前按 Token 鉴权方向规划，暂不采用 Cookie 承载认证凭据；两套后端遵循相同的登录交互、凭据传递约定和失效语义。
- Token 不直接等同于 JWT；采用不透明 Token 还是 JWT、通过何种请求头传递、前端如何存储、有效期及是否使用刷新 Token，均待进一步确定。
- Token 实现必须满足第一期规定的退出失效、账号禁用、密码修改或重置后旧凭据失效，以及授权变更及时生效要求；Java、Go 各自选择组件并验证。

## Spring Cloud 的使用边界（Java 后端）

Spring Cloud 已通过 2025.1.3 BOM 纳入 Java 版本管理；尚未添加具体 Cloud starter，也没有运行中的 Cloud 能力。待明确的是采用哪些组件，以及各组件解决什么实际问题。Go 后端不默认引入对应的整套分布式基础设施，按实际需求单独评估。

| 需要评估的能力 | 决策依据 | 当前状态 |
| --- | --- | --- |
| 网关与路由 | 是否需要统一入口，以及入口路由职责 | 待定 |
| 服务注册与发现 | 是否存在需要动态发现的独立服务 | 待定 |
| 配置管理 | 是否需要跨服务或跨实例统一管理配置 | 待定 |
| 服务间调用与容错 | 是否存在远程调用，以及失败处理需求 | 待定 |

采用 Spring Cloud 本身不能确定服务拆分方式。应先明确服务职责、数据边界和部署要求，再决定应用数量与组件组合，避免增加不必要的远程调用和运维成本。

无论采用何种拓扑，服务端都应执行接口权限及数据访问范围校验；前端可见性控制不能替代授权。若后续采用网关，也不能省略服务端的授权检查。

## 实施顺序与验收目标（规划）

详细功能范围、里程碑与验收清单见 [第一期功能规划](第一期功能规划_2026-10-19.md)。

1. 明确 Java、Go 与前端的版本及工具、Java 侧 Spring Cloud 使用范围、共同接口契约，以及首条功能链路需要的 PostgreSQL 版本、数据库配套工具和各自鉴权方案。
2. 初始化 `backend-template/java/`、`backend-template/go/` 与 `frontend-template/`，分别建立可验证的构建和启动方式，记录环境与配置要求。
3. 分别打通前端与两套后端的登录、角色权限和标准 CRUD 链路，覆盖分页、筛选、参数校验及错误反馈。
